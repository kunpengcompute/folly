# 小包合并：需求核对与验收

核对对象为历史测试快照 `eb9fcd695`，对照 2026-10-22 提供的
`URMA_SCALABLE_TRANSPORT_DESIGN.md` §8.1、§3.6、§12.3，以及
`URMA_IMPLEMENTATION_GAP_ANALYSIS.md` §2.7（URMA-07）。
差距清单评估的是另一个参考快照 `54e70e1a`，其中的问题不能直接当作本仓库的问题。

## 结论

**同一次写入的片段合并已实现；完整设计中的注册内存直发和共享队列路由尚未实现。**
本次补充可重复运行的验收程序及逐 WR / 逐写入统计，生产发送代码保持 `eb9fcd695` 不变。

| 需求 | 本仓库实现 / 核对结论 |
| --- | --- |
| 07.1 只读规划，提交失败不丢输入 | `Impl::flush()` 用 Cursor 复制连续前缀，不提前 pop 非空节点；`poll()` 收到成功完成后才消费原链。EAGAIN 与明确 RNR 保留字节。已实现。 |
| 07.2 总长、SGE 上限、节点中间分片 | 每次复制最多 `peerBuffer` 字节到已有注册块，固定 1 SGE；不受输入节点数量限制，可从节点中间继续。`max_sge=1` 已实现并实测。 |
| 07.3 不把节点数量当 RPC 数量 | SEND 承载连续的原协议字节，接收后交给原 parser；没有 `msg_count=num_sge` 或自行拆分 RPC。已实现。 |
| 07.4 同 socket、同次 writeChain 合并 | `flush()` 只读 `writes.front()`；独立写入保留各自回调，按 FIFO 完成。已有数据立即尝试发送，无凑包定时器。已实现。 |
| 上层已经 batch 的链 | 多个已编码 frame 作为一条链输入时连续打包，不解析 frame 内容。本次以 300+300+300 B 模拟这种链布局；不将它称为 Rocket 完整 RPC 验收。 |
| 空节点、共享 clone、普通未注册输入 | 空节点跳过；复制到 transport 的注册块，不写入原始数据或 headroom。已实测。 |
| 每 WR / 每 writeChain 统计 | 新增 `CoalescingTest`，输出 WR 字节数、SGE 数、逐写入 WR 数、排队时间和完成时间；观察逻辑只在测试进程内。 |

源码入口均在 `../UrmaAsyncSocket.cpp`：`createResources()`、`enqueue()`、
`flush()`、`poll()`、`finishWrite()`。2026-10-23 整理历史时，将 `6472412ba`
补充验收并入原 `eb9fcd695` 小包合并提交；v1 `2de955dba` 保持不变，
READ 保持后续独立提交。历史哈希用于追溯测试，生产代码内容未因合并改变。

## 与整体设计的区别

当前复制路径符合文档允许的注册块复制方式，但**不是注册正文零额外复制**。
文档的安全 headroom 原地加头、多 SGE 直发依赖注册范围管理等能力，仍属 URMA-03/08 后续工作。

当前连接独占收发端点，没有共享队列路由用的 H64。因此业务 SEND 的外层头占比为 0；
这不代表已经实现或优化掉了 H64，也不包含设备协议头及 TCP 建链开销。
共享端点、路由头、信用流控不在本次小包合并提交中引入。

文档中的 H64 是实际路由头；后续 READ 选路使用的 128 B 是用户指定的容量预留。
两者含义不同，不把预留解释成实际线上头部。

## 2026-10-22 补充双机结果

Clang 16.0.6；.145/.151 双向交换客户端角色；设备 `udmac0d1e2`；CPU 80–95、
内存 NUMA 0；加载库 SHA-256：
`0d3e53e7c797d1d2800bb142f69c169ffaae02a7f50a65339e3b3ff6cb7bc372`。

每连接连续排队 8 次独立写入：0、900、1024、0、3968、17、19、3968 B。
900 B 由三个 300 B 节点组成；1024 B 含空节点和多个片段；3968 B 同时覆盖分链和单节点。

| 协商容量 | 连接数 | 每连接写调用数 | 每连接成功 SEND 数 | 两个方向 |
| --- | --- | --- | --- | --- |
| 4096 B | 1 | 8 | 6 | 通过 |
| 4096 B | 3 | 8 | 6（进程共 18） | 通过 |
| 512 B | 1 | 8 | 22 | 通过 |
| 64 B | 1 | 8 | 157 | 通过 |

共 8 组、96 次写调用，逐字节回显、回调顺序、空写入零 SEND、共享输入未修改均通过。
每个实际 SEND 都只有 1 SGE，长度没有超过协商容量；17 B 和 19 B 的独立写入仍是两个 SEND。
这部分是带观察输出的正确性验收，**不是性能测量**。`queue_us` 从调用写入开始计时，包含握手等待及前序写入等待；空写入没有首次 SEND，记为 0。

性能结论仍使用 README 中无逐 WR 打印的旧 benchmark 三轮测试：1/4/8 KiB
平均延迟从 96.49/109.86/131.06 μs 变为 63.59/77.01/98.56 μs。
原有 41 组功能/异常检查及两端各 5 项生命周期检查的结果不因本次补充测试而重复计数。

## 重跑方法

在原 Folly 构建配置上增加 `-DFOLLY_BUILD_URMA_COALESCING_TESTS=ON`，
同时保持 `-DFOLLY_USE_URMA=ON -DBUILD_SHARED_LIBS=ON`，再构建：

```bash
cmake --build _build --target UrmaCoalescingTest -j8
```

两端均加载同版 Folly。先在服务端运行，再在客户端运行（IP、设备及绑核参数按实际机器填写）：

```bash
# 服务端
numactl -C 80-95 -m 0 ./_build/folly/io/async/urma/test/UrmaCoalescingTest \
  server 192.168.25.151 29565 udmac0d1e2 4096 1
# 客户端
numactl -C 80-95 -m 0 ./_build/folly/io/async/urma/test/UrmaCoalescingTest \
  client 192.168.25.151 29565 udmac0d1e2 4096 1
```

末两个参数分别是双方接收块容量和连接数；必须在两端一致。交换两端角色重复执行。
通过时输出 `PASS coalescing`，客户端另输出 WR 记录和逐写入 CSV。
测试仅适用于动态链接的 Linux URMA 环境；SDK 观察函数只链接进测试程序，不修改 Folly 或驱动。

512/64 B 分片用例用于 READ 引入前的纯 SEND 基线。启用 READ 后，这些配置会主动改变选路，
应改用 READ 边界用例验收；默认 4096 B 下本程序的非空写入均不超过 3968 B，可继续作为小包回归。
